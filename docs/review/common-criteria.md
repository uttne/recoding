# 共通レビュー基準（Common Review Criteria）

本ドキュメントは、技術スタックに依存しない AI エージェント向けの基本レビュー基準を定義する。
※`docs/review/project-criteria.md` と内容が競合する場合は、プロジェクト固有の `project-criteria.md` を優先する。

## 1. レビュー体制の原則
- **セルフレビューの禁止:** 実装を担当した子エージェント自身に最終レビューを行わせない。
- **独立した検証:** 親エージェント、または実装とは別のレビュー専用セッションが、**GitHub Issue の要件**と **git diff** を突き合わせて客観的に検証する。
- **推測の排除:** テスト・ビルド・型チェックの実行結果を必ず確認し、「おそらく動く」という推測で承認しない。

## 2. 4つの客観的チェック軸

### 軸 1：仕様整合性（Scope & Requirements）
- [ ] GitHub Issue の受け入れ条件（Acceptance Criteria）を漏れなく満たしているか。
- [ ] Issue のスコープ外の不要な変更（無関係なリファクタリング、フォーマット変更、設定変更など）が混入していないか。
- [ ] 仕様に曖昧な点があった場合、勝手な仮定で進めず、リスクとして報告できるよう記録しているか。

### 軸 2：エッジケースと安全性（Edge Cases & Security）
- [ ] 異常系（`null` / `undefined` / 空文字 / 空配列 / 境界値 / タイムアウト / ネットワークエラー等）でクラッシュや不整合が起きないか。
- [ ] 機密情報（API キー、トークン、パスワード、個人情報）のハードコードやログ出力がないか。
- [ ] 外部入力のバリデーション漏れ、インジェクション、権限チェック漏れがないか。

### 軸 3：テストの妥当性（Test Quality）
- [ ] 変更内容に対するテストが追加・更新され、すべてパスしているか。
- [ ] 実装をそのままなぞっただけの形骸化したテスト（常に成功するテストや過度なモック）になっていないか。
- [ ] 正常系だけでなく、主要な異常系・境界値も検証されているか。

### 軸 4：既存コードへの影響（Impact & Maintainability）
- [ ] 既存の設計パターン・命名規約・エラーハンドリング方針から大きく逸脱していないか。
- [ ] 既存の他機能・API・データ構造に対する破壊的変更がないか（ある場合は意図的かつ移行手順が明示されているか）。
- [ ] 不要なデバッグコード（`console.log`, `print`, コメントアウトされた旧コード等）が残っていないか。

## 3. 指摘の重要度分類

| 重要度 | 基準 | 対応 |
| :--- | :--- | :--- |
| **Must（修正必須）** | バグ、仕様漏れ、セキュリティ問題、テスト不足・失敗、破壊的変更、プロジェクト固有の禁止事項違反 | 子エージェントへ差し戻し、修正後に再レビューする |
| **Nice to have（提案）** | 命名の好み、軽微なリファクタリング、将来の拡張性に関する提案 | **差し戻さない**。レポートの「未対応の軽微な指摘」欄に記録するのみ |

## 4. 差し戻しとループ制御（無限ループ防止）
- 差し戻す際は、必ず **「対象ファイル・行番号」「問題点」「期待する修正方針」** を具体的に伝える。
- **リトライ上限は最大 2 回まで**とする。
- 2 回の差し戻しでも Must が解消しない場合は、それ以上ループせず作業を停止し、現状の差分・試したこと・詰まっている原因をまとめて **人間へエスカレーション** する。
